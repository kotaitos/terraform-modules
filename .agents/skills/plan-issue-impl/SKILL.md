# 実装計画スキル

GitHubのIssueを読み込み、詳細な実装計画に落とし込む。

## 前提条件

- 対象のIssue番号が指定されていること
- または、実装したい機能・修正内容が明確であること

## 実行手順

### 1. Issue内容の取得

```bash
# Issue詳細を取得
gh issue view <Issue番号>

# Issue本文のみ取得（パース用）
gh issue view <Issue番号> --json title,body,labels,assignees
```

### 2. Issue内容の分析

取得したIssueから以下を抽出・整理する：

| 項目 | 内容 |
|------|------|
| **目的** | このIssueで達成したいこと |
| **背景** | なぜこの変更が必要か |
| **スコープ** | 変更範囲（影響するコンポーネント） |
| **制約** | 技術的制約、互換性要件など |
| **受け入れ条件** | 完了の定義 |

### 3. コードベースの調査

関連するコードを調査し、現状を把握する：

```bash
# 関連する記述の検索（モジュール・雛形・スクリプト・ドキュメント）
rg "<関連キーワード>" modules templates scripts docs

# 似たことをしている既存モジュールを読む（実装パターンを踏襲するため）
ls modules/*/*
```

**調査観点:**
- **同じことをしている既存モジュールがないか。** あればその書き方に合わせる
  （変数の分け方、`validation` の粒度、README の構成）
- 変数・出力を変えるなら**破壊的変更になるか**
  （[module_contribution_guidelines.md](../../../docs/module_contribution_guidelines.md)
  「8. 後方互換性とリリース」）
- リソースアドレスが変わるなら `moved` ブロックで state を移せるか
- 追加する制約は `validation` で plan 時に落とせるか

### 4. 実装計画の作成

以下の構成で詳細な実装計画を作成する：

#### 4.1 概要

```markdown
## 概要

**Issue**: #<番号> <タイトル>
**目的**: <1-2文で目的を説明>
**影響範囲**: <変更が影響するコンポーネント>
```

#### 4.2 技術的アプローチ

```markdown
## 技術的アプローチ

### 選択したアプローチ
<採用するアプローチの説明>

### 代替案（検討したが採用しなかったもの）
- <代替案1>: <不採用の理由>
- <代替案2>: <不採用の理由>
```

#### 4.3 実装タスク

```markdown
## 実装タスク

### Phase 1: <フェーズ名>
- [ ] タスク1: <具体的な作業内容>
  - 対象ファイル: `path/to/file.py`
  - 変更内容: <何を変更するか>
- [ ] タスク2: <具体的な作業内容>

### Phase 2: <フェーズ名>
- [ ] タスク3: <具体的な作業内容>
```

#### 4.4 テスト計画

```markdown
## テスト計画

`terraform test`（`mock_provider` を使うので実際のリソースは作られない）に追加する run:

- [ ] 正常系: <確認する既定値・反映を確認する値>
- [ ] `reject_*`: <`expect_failures` で落ちることを確認する `validation`>

- [ ] `make preflight` が通ること（fmt / policy / validate / test / lint）
```

#### 4.5 リスクと考慮事項

```markdown
## リスクと考慮事項

| リスク | 影響度 | 対策 |
|--------|--------|------|
| <リスク1> | 高/中/低 | <対策> |
```

### 5. 実装計画のレビュー

作成した計画をユーザーに提示し、以下を確認：

- タスクの粒度は適切か
- 漏れている作業はないか
- 優先順位は正しいか
- 技術的アプローチに懸念はないか

## 出力形式

実装計画を以下の形式で出力：

```markdown
# 実装計画: #<Issue番号> <タイトル>

## 概要
...

## 技術的アプローチ
...

## 実装タスク
...

## テスト計画
...

## リスクと考慮事項
...

---
作成日: <日付>
関連Issue: #<番号>
```

## 注意事項

- 実装計画は具体的かつ実行可能なレベルで記述する
- 曖昧な表現（「適切に対応」「必要に応じて」など）を避ける
- 各タスクには対象ファイルや変更内容を明記する
- 大きなIssueは複数のPRに分割することを検討する
- 実装開始前にユーザーの承認を得る

## 関連スキル

- 実装計画が承認されたら、[commit-changes](../commit-changes/SKILL.md) でコミット
- PR作成時は [create-pr](../create-pr/SKILL.md) を使用
